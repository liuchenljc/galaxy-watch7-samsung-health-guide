# 06 · 配对与数据链路

> **环境事实（本机，2026-10-03）**
> - adb：`%USERPROFILE%\Desktop\platform-tools\adb.exe`（下文以 `$ADB` 代指，脚本开头 `ADB="%USERPROFILE%/Desktop/platform-tools/adb.exe"`）；手机：小米14（houji，HyperOS 3.0.306 / Android 16，已 root：SukiSU Ultra，su 可用），adb 序列号 `<SERIAL>`
> - 手表：Galaxy Watch7 SM-L310（One UI 8 Watch / Wear OS 16，蓝牙 MAC `<WATCH_MAC>`，Wear 节点 `<DEVICE_ID>`，**无 root**）；手机蓝牙 MAC `<PHONE_MAC>`（恢复出厂后会变）
> - 应用版本：三星健康 7.00.6.011 / 健康监测器(SHM) 1.5.2.002 / Galaxy Wearable 2.2.70 / Watch7插件 2.2.15 / 手表端 SHM 1.2.7.003（官方）
> - Git Bash 约定：所有 adb 批处理脚本开头必须 `export MSYS_NO_PATHCONV=1`；给 adb 的本地文件路径用 `C:/` 风格
> - 严重程度分级：P0=核心功能不可用；P1=绕过成本高；P2=一次性配置

## F1 · 弹『无法与 Galaxy Watch7 配对 — 需要先重置手表』（★ 先别重置！）

**影响范围**：手表↔手机全部通信 ｜ **严重程度**：P0

### ① 问题现象

Galaxy Wearable 弹「无法与 Galaxy Watch7 (PGLX) 配对 — 若要连接至此手机，您需要先重置手表，这会删除所有数据」。

### ② 报错关键信息（原文代码块）

```
无法与 Galaxy Watch7 (PGLX) 配对
若要连接至此手机，您需要先重置手表，这会删除所有数据
```

### ③ 根因分析

手机**恢复出厂**清空 /data 时**连同蓝牙配对密钥**一起清了：

- 手机侧 `/data/misc/bluedroid/bt_config.conf` 的已配对列表里没有手表（只剩别的设备）；
- 手表侧还绑着手机。

→ 两边不对称 → Galaxy Wearable 走『首次配对』向导 → 发现表被占用 → 要求重置。

### ④ 快速定位要点

三步，判断是『真丢』还是『误判』：

```bash
export MSYS_NO_PATHCONV=1
ADB="%USERPROFILE%/Desktop/platform-tools/adb.exe"

# ① 手机自己的蓝牙地址（恢复出厂后会变！本机 <PHONE_MAC>）
"$ADB" -s <SERIAL> shell settings get secure bluetooth_address

# ② 手机已配对列表里有没有手表（手机已 root；原文命令经 adb 调用、按层转义）
"$ADB" -s <SERIAL> shell "su -c 'grep -E \"^\\[[0-9a-f:]{17}\\]|^Name =\" /data/misc/bluedroid/bt_config.conf'"

# ③ 已配对（Bonded）设备列表
"$ADB" -s <SERIAL> shell dumpsys bluetooth_manager
```

判读：① 返回的是手机**自己的**地址（≠ 手表 MAC）；②③ 里**查不到手表 MAC**（<WATCH_MAC>）＝手机侧密钥真丢 → 走 ⑤；查得到则可能是误判，先核对归属（见 F2）。

### ⑤ 解决方案与操作步骤

**不删数据、不重置**：**手表：设置 → 连接 → 「连接到新手机」** → 手机上 Galaxy Wearable 重新配对。这个模式就是为『换手机但不想重置』设计的，**保留手表数据和应用**。

⚠️ 两个坑：

1. 弹窗的『确定』**不要点**（会引导重置）。
2. **手表的 MAC（<WATCH_MAC>）出现在手机侧三星应用的记录里是正常的**——那是手机在引用手表。曾把它误判成『手机的旧地址』而批量替换了 9 个数据库 400+ 处，靠事先 tar 备份回滚。**判断 MAC 归属必须先查该 MAC 的 Name 字段**（dumpsys bluetooth_manager / bt_config.conf 里 `<PHONE_MAC> = <OWNER_PHONE_NAME>` = 手机）。完整复盘见 F2。

副作用与善后：

- 重配会清掉手表上**侧载的 2 个 app**（GeminiMan、抗氧化启动器）→ 重装（一分钟，包在 `可选应用/` 目录），见 [05/E4](05_手表侧.md)。
- Galaxy Wearable 首次启动会弹条款页 → 点同意。这是正常流程，配对记录还在，不是真丢了。

### ⑥ 验证方式

- `bt_config.conf` 重新出现 `[<WATCH_MAC>] Name = Galaxy Watch7 (PGLX)`（用 ④② 的命令复核）；
- 蓝牙连接日志出现 `SecureConn:T`。

### ⑦ 预防措施

- 手机恢复出厂前就要预期到：蓝牙配对密钥会随 /data 一起清掉。重配走『连接到新手机』，**不要重置手表**。
- 以后见到『需要先重置手表』弹窗，先按 ④ 三步判断，再动手。

<a id="F2"></a>
## F2 · 误判蓝牙 MAC 归属，批量替换改坏配对记录 —— ★ 方法论级教训（含一次自造事故的完整复盘）

**影响范围**：差点破坏配对记录（幸有备份） ｜ **严重程度**：P0

### ① 问题现象

把手表的 MAC 当成手机的旧地址批量替换后，Galaxy Wearable 反而连不上（手机侧三应用的记录全被改坏）。

### ② 报错关键信息（原文代码块）

**无报错——是逻辑错误。** 判定依据链：

```
手机  settings get secure bluetooth_address = <PHONE_MAC>
手表  dumpsys bluetooth_manager → Bonded devices:
      <PHONE_MAC> = <OWNER_PHONE_NAME>     ← 这个 MAC 是手机，不是『手机的旧地址』
手表  <WATCH_MAC> 在 10-01 的连接记录里 = 手表（node <DEVICE_ID>）
```

### ③ 根因分析

凭『手机侧记录里搜不到某地址』反推归属，**没有先查该地址的 Name 字段**。

### ④ 快速定位要点

- **判定归属**：任何 MAC 先查 Name 字段——`dumpsys bluetooth_manager` / `bt_config.conf` 里 `<PHONE_MAC> = <OWNER_PHONE_NAME>` = 手机；`<WATCH_MAC>` 在 10-01 的连接记录里对应手表（node <DEVICE_ID>）。
- **找备份**：本会话改前就有 `/sdcard/wearable_fix_backup.tar.gz`。
- **还原前先停相关应用**（本会话停了 4 个应用）。

### ⑤ 解决方案与操作步骤

完整回滚（本会话因事先有 `/sdcard/wearable_fix_backup.tar.gz` 而**无损回滚**）：

```bash
export MSYS_NO_PATHCONV=1
ADB="%USERPROFILE%/Desktop/platform-tools/adb.exe"

# ① 备份（改前必须做；本会话即因它而能无损回滚）
"$ADB" -s <SERIAL> shell "su -c 'tar -czf /sdcard/backup.tar.gz -C /data/data <相关应用目录>'"

# ② 停应用 → 解包还原（本会话：停 4 个应用）
"$ADB" -s <SERIAL> shell "su -c 'am force-stop <应用包名>'"
"$ADB" -s <SERIAL> shell "su -c 'tar -xzf /sdcard/wearable_fix_backup.tar.gz -C /data/data'"

# ③ 验证：手表地址出现次数恢复、手机地址 0 残留（本会话：82 处恢复 / 0 残留）
"$ADB" -s <SERIAL> shell "su -c 'grep -r <手表MAC或关键字> /data/data/<相关应用目录>'"
```

权限归属 tar 会一并恢复。

### ⑥ 验证方式

- 还原后 Galaxy Wearable 行为与改前一致；
- prefs 里手表地址计数恢复（本会话：手表地址 82 处恢复、手机地址 0 残留）。

### ⑦ 预防措施

**批量替换前必须：**

1. **确认每个地址/值的归属（查 Name 字段）**；
2. **先备份**；
3. **改完立即做行为验证**。

此条已写入恢复清单文档。

## F3 · 『无法在手机上打开三星健康』（Wear 数据层节点未连接）

**影响范围**：三星健康↔手表的全部 GMS 通道功能（含 AGEs/抗氧化入口跳转） ｜ **严重程度**：P0

### ① 问题现象

- 手表端功能提示『无法在手机上打开三星健康』；或 Galaxy Wearable 里操作三星健康相关项失败。
- 注意：**AGEs 页面提示『更新三星健康』也是同一个原因的误报**——数据层不通时，三星健康会把连接问题误报成版本问题。

### ② 报错关键信息（原文代码块）

```
E/SHEALTH#WI#GmsWearableHelper: Failure sendMessageAwait4000: TARGET_NODE_NOT_CONNECTED
```

（GMS Wear API 4000。）

### ③ 根因分析

**Wear OS 数据层的节点注册表未刷新**。

- 承载方是**国行版** `com.google.android.wearable.app.cn`（**不是**国际版 `com.google.android.wearable.app`——后者连数据库目录都没有，排查时别找错）；
- node.db 在 `/data/data/com.google.android.wearable.app.cn/databases/node.db`；
- 手表重配/蓝牙重连后节点表可能陈旧。

### ④ 快速定位要点

```bash
"$ADB" -s <SERIAL> logcat -d | grep 'SHEALTH#WI'    # 看 TARGET_NODE_NOT_CONNECTED
```

⚠️ **`logcat | grep -c` 会把你自己的 grep 命令行记进日志（adbd tag）造成假阳性**——要看时间戳，或排除 adbd 相关行（如再接 `| grep -v adbd`）。

### ⑤ 解决方案与操作步骤

```bash
export MSYS_NO_PATHCONV=1
ADB="%USERPROFILE%/Desktop/platform-tools/adb.exe"

"$ADB" -s <SERIAL> shell "su -c 'am force-stop com.google.android.wearable.app.cn'"
"$ADB" -s <SERIAL> shell "su -c 'am force-stop com.google.android.gms'"

# 等十几秒自动重建（进程会自动拉起，含 :background / :migrate 子进程）
```

### ⑥ 验证方式

- 重新触发操作，不再报 `TARGET_NODE_NOT_CONNECTED`；
- 手机蓝牙与手表 `SecureConn:T`；
- 手表设置项（如亮度）变化能实时同步到手机（`WatchSettings_Watch7` 日志）→ 数据层活了。

### ⑦ 预防措施

手表重配/蓝牙重连后，若三星系应用报连接问题，**先刷数据层再查别的**。
