<a id="G1"></a>
## G1 · logcat 判据『明明修好了还报错』（grep 自我匹配陷阱）

**影响范围**：所有基于 logcat 的判据 ｜ **严重程度**：P0

### 现象
修复动作做完，`logcat -d | grep -c 'TARGET_NODE_NOT_CONNECTED'` 计数仍是 1，以为没修好。

### 报错关键信息
logcat 里出现：

```text
I/adbd: in ShellService: logcat -d ... | grep -ac 'TARGET_NODE_NOT_CONNECTED'
```

——**你的 grep 命令行本身被 adbd 记进了日志**。

### 根因
通过 adb shell 跑的每条命令都会被 adbd 记入 logcat；grep 的模式串出现在命令行里 → 自我匹配。

### 快速定位
- 看匹配行的**时间戳**：是修复前还是修复后；
- 或看该行 **tag 是否为 adbd**。

### 解决方案
1. 按时间戳过滤：只统计修复时刻之后的行才算；
2. `grep -av adbd`：排除 adbd 自身记录的命令行；
3. **字符类打断**模式串，让日志里的命令行匹配不上自己：
   - `grep 'not supported i[n]'`
   - `grep 'S HealthMonitor - Rin[g]'`
4. 限行数、缩窗口：`logcat -d -t 300`。

### 验证
修复后新产生的日志段里计数为 0。

### 预防
所有 logcat 判据脚本统一用『**字符类打断 + 排除 adbd + 限时间窗**』。

## G2 · 判据脚本恒为 false（grep -c / 键名 / 引号三连坑）

**影响范围**：所有自动化判据脚本 ｜ **严重程度**：P1

### 现象
断言脚本永远走失败分支。

### 报错关键信息
`grep -c setup_init prefs.xml` 输出 `1`，但脚本断言 `"setup_init" in out` 恒 False。

### 根因（三连）
1. **`grep -c` 只输出数字，不含键名** → 用关键字 `in` 判断恒 False，**要解析整数**：
   `int(re.search(r'(\d+)', out).group(1))`
2. **键名不精确**：
   - 正确键名是 `tracker_bloodpressure_timestamp`（无下划线），不是 `tracker_blood_pressure`；
   - `tracker_bloodpressure_accessory_data_count` 是『配饰同步』通道计数（SHM 走 Health Data API 不更新它，恒 0），不是血压判据。
3. **`sh()` 包装会把命令包成 `su -c '...'`**，正则里的单引号与之嵌套冲突 → 用字符类打断（`i[n]`、`blood[_]?pressure`）。

### 快速定位
把命令原样在 shell 里跑一遍，看原始输出长什么样。

### 解决方案
判据改为：解析数字 / 精确键名 / 字符类打断。

### 验证
判据在已知状态（好/坏各一次）下分别返回 true/false。

### 预防
写判据前先手工跑一遍命令看原始输出。

## G3 · SHM 的 prefs 加密读不出值

**影响范围**：SHM 状态验证 ｜ **严重程度**：P1

### 现象
想验证某个开关（如 `ecg_tnc_complete`）是否写入，打开 SHM 的 shared_prefs 发现值是 `Base64(iv)#Base64(ct)` 格式。

### 报错关键信息
无报错。判据就是**值本身的格式**：形如 `Base64(iv)#Base64(ct)`（`#` 分隔的两段 Base64）= 已加密值——键名明文可见、值离线不可读；靠该格式判定"读不出是加密所致，不是键不存在"。

### 根因
AES-GCM 加密，密钥由 Android Keystore 持有（KeyGenParameterSpec tag `S Health Monitor - DataKeyUtil`，util/d.d() 生成），**离线不可解**。

### 快速定位
- 值里带 `#` 分隔的两段 Base64 = 加密值；
- 明文键名可见，但值不可读。

### 解决方案
**放弃读值，全部改用行为观测**：
1. logcat 判据（`[parseIntent] isAppInitialized`、`OnboardingUtil current Network : XX`）；
2. deep-link 报文（Node.send body）；
3. UI 渲染（卡片是否出现）；
4. 数据库文件大小变化（RoomSHealthMonitorEcg.db 28KB→167KB）；
5. sync_history 表（三星健康侧的同步记录）。

### 验证
行为判据与功能实际状态一致（好/坏各验一次）。

### 预防
方案设计阶段就不要依赖『读加密 prefs』的验证路径。

## G4 · 通用诊断方法论（速查）

**影响范围**：所有排查 ｜ **严重程度**：P0（方法论级）

1. **『手机毫无反应』先查 MIUI 拦截**——日志指纹 `Permission Denied Activity`，别先怀疑应用。
2. **『改了没效果』先确认改动真的被加载 + 被读到**——加载靠在代码里打版本标记日志确认；进程内实际值可能和预期不同（如 `Build.MANUFACTURER` 冻结问题）。
3. **『本地问题还是服务端问题』用断网实验一步定位**——`svc data disable; svc wifi disable`。
4. **动手批量改之前先 tar 备份**——本会话靠它无损回滚了一次自造事故。
5. **多设备环境所有 adb 命令一律 `-s <serial>`**。
6. **判断地址/标识归属必须查 Name 字段**——不能靠『搜不到』反推。
7. **每次改完在代码里打带版本标记的日志**——一眼确认运行的是哪一版。
8. **找『正在运行的版本』而不是『手上的旧源码』**——`pm path` → `pull` → `baksmali`。
