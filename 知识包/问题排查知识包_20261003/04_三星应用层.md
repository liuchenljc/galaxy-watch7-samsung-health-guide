# 04 · 三星应用层（SHM / 三星健康）

> 本文件是知识包里分量最重的一份，覆盖三星应用层 7 个问题（D1～D7）。**D3（`shealth_monitor_base_app_setup_init` 总开关）是本次项目的核心突破**：血压下发与 ECG 条款握手两大核心功能的『死锁』共用这一个病根，不是两个问题。**D1 / D2 是前置问题**：D1 卡死三星健康 OOBE，D2 的入口改道又跳过了 SHM 初始化链——正是 D2 的副作用让 D3 的病根被触发，D2 修完必须接着做 D3。**D4（地区门）是独立问题**，与 D1～D3 无因果。**D5～D7 是外围问题**（双包干扰 / SAP 进程复活 / 数据权限），按需排查。

**严重程度口径**（与 README 第四节一致）：P0=核心功能不可用；P1=绕过成本高；P2=一次性配置。
**占位约定**：形如 `<...>` 的是需按现场替换的动态值；其余命令中的 adb 路径、序列号均为本机实测值，可直接复制。

**本机环境速查**

- adb：`%USERPROFILE%\Desktop\platform-tools\adb.exe`（Git Bash 里写 `%USERPROFILE%/Desktop/platform-tools/adb.exe`）；所有 adb 批处理**开头必须 `export MSYS_NO_PATHCONV=1`**，给 adb 的本地路径一律 `C:/` 风格
- 手机：小米 14（houji），HyperOS 3.0.306 / Android 16，序列号 `<SERIAL>`，已 root（SukiSU Ultra，`su` 可用）
- 手表：Galaxy Watch7 SM-L310（One UI 8 Watch / Wear OS 16），蓝牙 MAC `<WATCH_MAC>`，Wear 节点 `<DEVICE_ID>`，无 root；无线 adb 地址与端口**每次都会变**（用 `adb mdns services` 重新发现）

<a id="D1"></a>
## D1 · 三星健康卡在登录页出不去（三星账户分包损坏）

**影响范围**：三星健康 OOBE ｜ **严重程度**：P0

### ① 问题现象

三星健康 7.x 在非三星手机上首次启动强制三星账户登录：页面只有『登录』按钮、没有『跳过』；点『登录』手机无任何反应。三星账户进程在后台循环崩溃（logcat 里 pid 一个接一个换新）。

### ② 报错关键信息

```
ClassNotFoundException: Didn't find class "com.samsung.android.samsungaccount.SamsungAccountApp"
com.samsung.android.samsungaccount.permission.ACCOUNT_MANAGER: granted=false
```

进程循环崩溃：同一异常的 pid 一个接一个。`granted=false` 是崩溃现场的伴生现象，排障以 `ClassNotFoundException` 为主判据。

### ③ 根因分析

- 三星账户 App 的**真实包名是 `com.osp.app.signin`**。⚠️ 它**不是** `com.samsung.android.samsungaccount`——报错里的 `com.samsung.android.samsungaccount.*` 只是它声明/引用的权限与类名空间；按 `samsungaccount` 关键字去 `pm list packages` 里搜已装包，会漏掉真正的元凶。
- 三星账户是**分包（split APK）应用**，但只装进了 `base.apk`：`/data/app/.../` 安装目录下没有任何 `split_config.*.apk`。运行时按 ABI/density 去 split 里找 `SamsungAccountApp` 找不到 → 一启动就 `ClassNotFoundException` → 循环崩溃 → 『登录』按钮拉不起任何界面。

### ④ 快速定位要点

先看什么：logcat 崩溃循环；再查什么：三星账户的包名与安装目录里有没有 split。

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 1) ⚠️ 按 osp.app.signin 搜（按 samsungaccount 搜会漏）
"$A" -s $S shell pm list packages | grep -i "osp.app.signin"

# 2) 看它声明了哪些 apk：只输出一行 base.apk = 只装了 base（中招）
"$A" -s $S shell pm path com.osp.app.signin

# 3) 目录级确认：正常应能看到多个 split_config.*.apk
"$A" -s $S shell su -c 'ls -l /data/app/*osp*/'

# 4) 崩溃循环证据
"$A" -s $S logcat -d | grep -E "ClassNotFoundException|SamsungAccountApp|ACCOUNT_MANAGER"
```

### ⑤ 解决方案与操作步骤

两条路线二选一：

**路线 A：重装完整分包（通用解）**

1. 从 APKMirror 下载三星账户的 `.apkm` **整包**（含全部 split），用 SAI（Split APKs Installer）安装；
2. 或把各 split 拉到本地后 `adb install-multiple` 安装；
3. **必须三星原签名**——重打包/第三方签名装不上，装上也过不了账户鉴权。

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# install-multiple 示例：split 文件清单以 .apkm 解包 / pm path 输出为准
"$A" -s $S install-multiple base.apk <split_config.arm64_v8a.apk> <split_config.xxhdpi.apk> ...
```

**路线 B：KCB 绕过（本项目最终采用）**

用 LSPosed（Vector）hook 中国版构建检查 `fs90.u()` 使其返回 `true`，让 OOBE 判定当前构建无需真登录，直接放行（不再要求真账户登录）。

### ⑥ 验证方式

- 路线 A：三星健康里点『登录』能拉起三星账户界面，不再闪退。
- 路线 B：OOBE 直接放行，不再卡登录页。
- 复查分包完整：`"$A" -s $S shell pm path com.osp.app.signin` 输出多行（base + splits）。

### ⑦ 预防措施

- 非三星手机上装三星账户，**务必用完整分包**（.apkm 整包 / SAI / install-multiple）；单 base.apk 是隐性炸弹。
- 记住包名映射：三星账户 = `com.osp.app.signin`，搜索排障时别用错关键字。

## D2 · SHM 打开即退（入口厂商白名单）

**影响范围**：SHM 可用性 ｜ **严重程度**：P0

### ① 问题现象

三星健康监测器（SHM，`com.samsung.android.shealthmonitor`）点开就退 / 闪退，进不了任何界面。

### ② 报错关键信息

没有崩溃栈，判据是 logcat 里 onCreate 前后段**不成对**：

```
[PERF] onCreate - start
（没有对应的 [PERF] onCreate - end）
```

### ③ 根因分析

smali 级证据：`MainActivity.onCreate` 首段判定：

```java
Build.MANUFACTURER.toLowerCase().contains("samsung")
```

小米机上为 `false` → 直接走 `finish(); return-void`，onCreate 提前返回。这是 SHM 硬编码的厂商白名单，不是兼容性 bug。logcat 只有 `[PERF] onCreate - start` 而没有 `- end`，就是在 onCreate 里提前 return 的直接证据。

### ④ 快速定位要点

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

"$A" -s $S logcat -c
# —— 手机上点开 SHM ——
"$A" -s $S logcat -d | grep -E "PERF|shealthmonitor"
# 只有 [PERF] onCreate - start、没有 - end = onCreate 内提前 return（本问题签名）
```

smali 侧：反编译 SHM，看 `MainActivity.onCreate` 首段的 `MANUFACTURER` 分支与 `finish(); return-void`。

### ⑤ 解决方案与操作步骤

LSPosed（Vector）hook `MainActivity.onCreate`：`proceed()` 之后**无条件**执行 `startActivity(SHealthMonitorMainActivity)`——把入口改道到真正的主界面，绕过厂商判定。

⚠️ **教训**：曾试过用 `isFinishing()` 做条件改道（检测到 finish 才改道），实测该 ROM 上该判据不可靠 → 改为**无条件改道**。

⚠️ **副作用（重要）**：无条件改道会跳过 `SetupActivity → ProfileEditActivity` 的初始化链——这正是 D3 病根被触发的连锁后果（后来才发现）。**D2 修复后必须接着做 D3**，能进主界面 ≠ 初始化链走完。

### ⑥ 验证方式

SHM 点开能进主界面（不再闪退）。

### ⑦ 预防措施

- 厂商白名单类『打开即退』先查 onCreate 提前 return（logcat 的 `[PERF]` start/end 成对性），再查崩溃栈。
- D2 的 hook 改动要与 D3 联动验收，防止『能打开但功能死锁』的假性修复。

<a id="D3"></a>
## D3 · ★ setup_init 总开关：血压与心电图『死锁』的共同病根（本次项目核心突破）

**影响范围**：血压下发 + ECG 条款握手（两大核心功能） ｜ **严重程度**：P0

### ① 问题现象

三组表现，一个病根：

1. 手表提示『到手机上操作』↔ 手机提示『去手表上弄』，两边互相踢皮球的死循环；
2. 手机→手表的测量指令被**静默丢弃**（无报错、无异常日志）；
3. 手表永远收不到『条款已完成』——ECG 侧表现为手表收不到 tnc_sync 广播。

### ② 报错关键信息

```
[parseIntent] isAppInitialized = false, isValidAge = true
```

deep-link 入口判据：`isAppInitialized = false` 就直接 `finish()`。ECG 侧表现为手表收不到 `com.samsung.android.shealthmonitor.common.tnc_sync` 广播。

### ③ 根因分析

**误判史**：此前先后猜过 ① 手表↔手机加密协议问题、② 手表固件地区门、③ deep-link 校验——三个方向全部被 2026-10-02 的代码级分析（smali）证伪。真正的病根如下：

- SHM 的 pref **`shealth_monitor_base_app_setup_init` 默认 false**，且**只由「创建个人资料」页的保存按钮写入**（smali 证据：`ld/e0.smali` 的 `:cond_5e` 分支：`shealth_monitor_base_app_setup_init` → TRUE）。
- `ActionRequestActivity.onCreate` 三重判据：`isAppInitialized` + `isValidAge`（生日 ≥22 岁），任一不过就 `finish()`——这就是手机→手表指令被静默丢弃的直接原因。
- 初始化链又被 D2 的入口改道**跳过** → 该键永远没机会写入。
- ECG 死锁是同一病根：`SetupActivity.synchronizeTnc()`（挂在初始化链上）负责广播 `com.samsung.android.shealthmonitor.common.tnc_sync`（`EcgBroadcastReceiver`，`exported=false`），经 SAP 通知手表『条款已完成』；初始化链没走 → tnc_sync 不发 → ECG 握手死锁。
- **结论：血压与 ECG 是同一个病根，不是两个问题。**

### ④ 快速定位要点

先看 deep-link 判据日志，再查 prefs 键是否存在（注意 `grep -c` 只输出数字；多文件时输出为 `文件名:数字`）：

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 1) 入口判据（false = 病根在）
"$A" -s $S logcat -d | grep parseIntent

# 2) prefs 键存在性（0 = 未初始化）
#    pref 值本体是加密的（Base64(iv)#Base64(ct)，见 D7/G3），grep 只能确认键存在，读不出值
"$A" -s $S shell su -c "grep -c setup_init /data/data/com.samsung.android.shealthmonitor/shared_prefs/*.xml"
```

### ⑤ 解决方案与操作步骤

三步（前两步后来被验证有效）：

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# ① 直接拉起 SHM 条款页（条款已同意则自动跳过 → 进入「创建个人资料」）
"$A" -s $S shell su -c 'am start -n com.samsung.android.shealthmonitor/com.samsung.android.shealthmonitor.home.ui.activity.SHealthMonitorSetupActivity'

# ② 人工手点（root input tap 在该 ROM 上不可靠，见 D7/C3）：
#    - 改一下出生日期，让『保存』按钮由灰变亮（云恢复的字段不算用户输入）
#    - 生日填 2004 年或更早（≥22 岁，满足 isValidAge）
#    - 选性别 → 点『保存』
#    （保存后自动返回上一页是正常行为，不是故障）

# ③ 拉起 SAP 传输进程（同 D6；receiver exported=0 必须 root）
"$A" -s $S shell su -c 'am broadcast -a android.accessory.device.action.CONNECT -n com.samsung.accessory/.receivers.SAFrameworkStartTriggerReceiver'
```

### ⑥ 验证方式

分层判据（全部实测通过）：

```bash

A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
```

### ⑦ 预防措施

- **手机恢复出厂 / 换机后必须重做本节三步**（已写入 README 第三节的重建顺序，最容易漏）。

- `bp_module_disable_state` 超时也是设计如此（三星源码注释原话：*'Wear won't send ... response ... but it is a normal operation. Don't worry'*）。

<a id="D4"></a>
## D4 · 地区门：『服务不可用 — 在您当前的位置不可用』

**影响范围**：SHM 全部地区门控功能（血压/ECG/睡眠呼吸暂停） ｜ **严重程度**：P0

### ① 问题现象

- SHM 页面显示『服务不可用 — 在您当前的位置不可用』；
- 或标签栏少功能（如睡眠呼吸暂停标签不出现）；
- 或先出现校准页，约 1 分钟后被翻回『不可用』。

### ② 报错关键信息

```
OnboardingUtil current Network : CN            ← 修复前实测（地区门在拦）
[isSupportCountry] CSC = VN, isSupported = true   ← 修复后期望（实测）
```

### ③ 根因分析

地区判定是**多源的，缺一不可**：

| 源 | 内容 | 说明 |
|---|---|---|
| ① CSC 属性 | `ro.csc.sales_code=XXV` / `ro.csc.countryiso_code=VN` / `ro.csc.iso_code=VN` | SHM 经 `SemSystemProperties` 读取；该类在非三星上缺 → `ClassNotFoundException` → 自动回退标准 `SystemProperties.get` |
| ② SIM/网络国家 | `TelephonyManager.getNetworkCountryIso()` / `getSimCountryIso()` | OnboardingUtil 日志可见（修复前 `current Network : CN`） |

- 断网实验（`svc data disable; svc wifi disable` 后行为不变）证实**100% 本地判定**：服务端 / VPN / Clash 全部无关。
- 只改①会被②翻回：校准页出现约 1 分钟后被翻回『不可用』；只改②：标签解锁但血压页不可用；**两个都改才稳定**。

**⚠️ 连带结论**：`Build.MANUFACTURER` 在 zygote 开机时冻结（`Build` 是启动类，静态字段 COW 共享），**运行时 resetprop 对 `Build.*` 无效**（getprop 变了但应用内不变，同 B4）——不要试图运行时改厂商属性骗过白名单。

### ④ 快速定位要点

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 1) 三条 CSC 属性现状
"$A" -s $S shell getprop ro.csc.sales_code
"$A" -s $S shell getprop ro.csc.countryiso_code
"$A" -s $S shell getprop ro.csc.iso_code

# 2) SHM 的两个判定日志
"$A" -s $S logcat -d | grep -E "isSupportCountry|OnboardingUtil"

# 3) 断网实验（可选，证伪服务端/代理因素；测完立刻恢复网络）
"$A" -s $S shell su -c 'svc data disable; svc wifi disable'
"$A" -s $S shell su -c 'svc data enable; svc wifi enable'
```

### ⑤ 解决方案与操作步骤

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# ① resetprop 三条 CSC 属性（XXV/VN）
"$A" -s $S shell su -c 'resetprop ro.csc.sales_code XXV'
"$A" -s $S shell su -c 'resetprop ro.csc.countryiso_code VN'
"$A" -s $S shell su -c 'resetprop ro.csc.iso_code VN'

# ② LSPosed（Vector）hook：TelephonyManager.getNetworkCountryIso() 与
#    getSimCountryIso()，proceed() 之后覆盖返回值为 "vn"

# ③ force-stop SHM 后重开（让两个判定源同时生效）
"$A" -s $S shell su -c 'am force-stop com.samsung.android.shealthmonitor'
```

注意：resetprop 改的是**运行时属性，重启即失效**——持久化需写进开机脚本（如 KSU 模块 service.sh，可与 D6 的 ensure_sap() 同处维护）。

### ⑥ 验证方式

分层验证：

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

"$A" -s $S logcat -d | grep -E "isSupportCountry|OnboardingUtil"
# 期望：[isSupportCountry] CSC = VN, isSupported = true
#       OnboardingUtil current Network : VN
```

- 血压页出现「校准手表」按钮，且 **100 秒不翻回**『不可用』；
- 标签栏变为 3 个（睡眠呼吸暂停标签出现）。

地区对照（实测）：

| CSC / 国家 | 血压 | ECG |
|---|---|---|
| XXV / VN | ✅ 已批 | ✅ 已批 |
| CHC / CN | ❌ | ✅ |
| US | ❌（血压未批） | —（本次未验证） |

### ⑦ 预防措施

- 恢复出厂 / 换机后按 ①②③ 全套重做；只做一半必然翻回。
- resetprop 的 CSC 属性写入开机脚本持久化（KSU 模块 service.sh）。
- 别再用运行时改 `Build.*` 属性的方式骗厂商白名单（见根因分析的连带结论 / B4）。

<a id="D5"></a>
## D5 · 双 SHM 包互相干扰（dante63 mod 残留）

**影响范围**：SHM 握手可靠性 ｜ **严重程度**：P2

### ① 问题现象

装过 dante63 mod（包名 `com.samsung.android.shealthmonitors`，**多个 s**；versionName 带 `.dante63` 后缀）后又装了官方版（`com.samsung.android.shealthmonitor`），旧 mod 进程仍然活着。

### ② 报错关键信息

```
# 两个包同时在场：
com.samsung.android.shealthmonitor    ← 官方（单个 s）
com.samsung.android.shealthmonitors   ← dante63 mod（多个 s）

ps -A | grep shealthmonitors          # 有输出 = 旧 mod 进程存活
```

### ③ 根因分析

- 两个包名只差一个结尾的 s：官方 `com.samsung.android.shealthmonitor` vs dante63 watch mod 的手机端包 `com.samsung.android.shealthmonitors`（**多个 s**）。
- 旧 mod（1.2.1.009，2024 年版）没有被卸载，进程存活，可能干扰官方版（1.5.2.002）的握手。
- 卸载时用 `-k --user 0` 保留数据，可回滚。

### ④ 快速定位要点

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 两个包都在 = 中招
"$A" -s $S shell pm list packages | grep shealthmonitor

# 确认旧 mod 的版本与安装路径
"$A" -s $S shell dumpsys package com.samsung.android.shealthmonitors | grep -E "versionName|codePath"

# 旧 mod 进程是否存活
"$A" -s $S shell ps -A | grep shealthmonitors
```

### ⑤ 解决方案与操作步骤

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 1) 先备份旧 mod APK（pm path 可能输出多行，base + splits 都拉）
"$A" -s $S shell pm path com.samsung.android.shealthmonitors
"$A" -s $S pull <pm path 输出的 apk 路径> C:/<本地备份目录>/

# 2) 卸载旧 mod（-k 保留数据，可回滚）
"$A" -s $S shell pm uninstall -k --user 0 com.samsung.android.shealthmonitors
```

### ⑥ 验证方式

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

"$A" -s $S shell ps -A | grep shealthmonitors   # 无输出 = 已清除
"$A" -s $S shell dumpsys package com.samsung.android.shealthmonitor | grep versionName
# 官方包 versionName 正常（1.5.2.002）
```

### ⑦ 预防措施

- 分清两个包名：**多个 s = dante63 watch mod**（versionName 带 `.dante63` 后缀）。
- 不要用 dante mod 的手机端包替代官方 SHM。

## D6 · SAP 传输进程不自动复活

**影响范围**：所有 SHM↔手表消息 ｜ **严重程度**：P1

### ① 问题现象

手表↔手机消息发不出；SAP 连接状态 LISTENING 但零连接。

### ② 报错关键信息

```
pidof com.samsung.accessory     → （空输出，进程不存在）
SAP 连接状态                     → LISTENING，但连接数 0
（无崩溃、无报错日志——进程死了是静默的）
```

### ③ 根因分析

- `com.samsung.accessory` **没有任何 launcher activity**——桌面上没有图标可点，无法手动拉起。
- 把它改成 noRestrict（解除后台限制）后**进程也不会自动复活**——必须显式拉起。

### ④ 快速定位要点

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

"$A" -s $S shell pidof com.samsung.accessory    # 空输出 = 进程死了
"$A" -s $S shell ps -A | grep samsung.accessory # 交叉确认
```

### ⑤ 解决方案与操作步骤

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 显式拉起 SAP 传输进程
# ⚠️ receiver exported=0，shell 身份会被拒 → 必须走 root（su -c）
"$A" -s $S shell su -c 'am broadcast -a android.accessory.device.action.CONNECT -n com.samsung.accessory/.receivers.SAFrameworkStartTriggerReceiver'
```

### ⑥ 验证方式

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

"$A" -s $S shell pidof com.samsung.accessory   # 有输出 = 进程复活
```

随后 SHM↔手表消息恢复（D3 的验证链路可通）。

### ⑦ 预防措施

- 并入 KSU 模块（shm_watch7_fix）的 `service.sh`：`ensure_sap()` 在每轮自愈时 `pidof` 检查、空则显式拉起。

## D7 · 数据权限总开关点不动（SHM 有数据、三星健康无记录）

**影响范围**：SHM→三星健康的数据展示 ｜ **严重程度**：P2

### ① 问题现象

SHM 数据库里有数据（如 `RoomSHealthMonitorBp.db` 在增长），但三星健康里看不到记录（血压/心电图卡片无数据）。

### ② 报错关键信息

无崩溃报错，判定靠两个观测面：

```
# SHM 侧：数据库在长
$ ls -l /data/data/com.samsung.android.shealthmonitor/databases/RoomSHealthMonitorBp.db
# 三星健康侧：血压/心电图卡片无数据
```

### ③ 根因分析

- SHM→三星健康的数据读写需要『数据权限』授权。
- SHM 同步时会自动弹出「数据权限」弹窗；总开关『所有权限』需要打开——不开则数据过不去。

### ④ 快速定位要点

```bash
export MSYS_NO_PATHCONV=1
A="%USERPROFILE%/Desktop/platform-tools/adb.exe"
S=<SERIAL>

# 1) SHM 侧数据是否在增长（隔几分钟查两次对比大小）
"$A" -s $S shell su -c 'ls -l /data/data/com.samsung.android.shealthmonitor/databases/ | grep -E "RoomSHealthMonitor(Bp|Ecg)"'

# 2) 确认 prefs 加密在生效（只能看到密文，读不出值——同 G3）
#    值形如 Base64(iv)#Base64(ct)；AES 密钥在 Android Keystore，tag 'S Health Monitor - DataKeyUtil'
"$A" -s $S shell su -c 'ls /data/data/com.samsung.android.shealthmonitor/shared_prefs/'
```

### ⑤ 解决方案与操作步骤

1. 等弹窗出现（SHM 同步触发）→ **人工手点**总开关『所有权限』→ 完成。
2. 也可以在三星健康 → 设置里找数据权限入口。

⚠️ 坑：

- **MIUI 吞合成触摸**（见 C3，03_MIUI拦截三件套.md）：root `input tap` 点总开关可能无效（实测点击后 enabled 状态不变）→ 关键开关必须人工手指点。
- **SHM 的 prefs 是加密的**（Base64(iv)#Base64(ct)，AES 密钥在 Android Keystore，tag 'S Health Monitor - DataKeyUtil'）→ **无法读值验证**授权状态，只能行为观测。

### ⑥ 验证方式

- 三星健康里血压/心电图卡片出现数据；
- 或 SHM 数据库继续增长（`ls -l` 两次对比大小）。
- 无法通过读 prefs 验证（加密，见 ④）。

### ⑦ 预防措施

- 恢复出厂 / 重装 SHM 后，首次同步时留意「数据权限」弹窗，当场把『所有权限』打开。
- MIUI 吞合成触摸的问题存在于所有需要 UI 点击的自动化（见 C3）——关键开关一律人工手点。
